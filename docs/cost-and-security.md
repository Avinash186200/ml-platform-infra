# Cost and security notes

## Cost

I give no dollar figures: nothing was applied, so there is no bill to quote, and list prices change. Use the AWS Pricing Calculator with the components below. In rough order of size for the dev environment as configured:

| component | what you pay for | dev setting | lever |
|---|---|---|---|
| EKS nodes | instance hours | 2 x t3.large on demand (min 1, max 4) | SPOT capacity (`node_capacity_type`), smaller instances, scale to 1 overnight |
| EKS control plane | a fixed hourly fee per cluster | 1 cluster | share one cluster across environments with namespaces, if the team accepts the blast radius |
| NAT gateway | hourly fee plus per-GB processed | 1 for the VPC | the S3 gateway endpoint already keeps artifact traffic off the NAT; image pulls from ECR still use it (an ECR interface endpoint removes that, at its own hourly cost) |
| ElastiCache | node hours | 1 x cache.t4g.small, no replica | fine for dev; prod wants `redis_replicas = 1` (doubles this line) |
| CloudWatch logs | ingestion and storage | EKS control-plane logs (all 5 types), flow logs (rejects only), 30-day retention | drop `controllerManager`/`scheduler` logs in dev; they are the noisiest |
| S3 | storage, requests | snapshots kept until pruned by hand (runbook), old object versions expire after 30 days | storage is not the issue at this data size; request counts from many pods polling `CURRENT` every 15-30 s are small but not zero |
| KMS | per key per month plus requests | 2 keys, S3 bucket keys on (fewer KMS calls) | already minimal |
| ECR, Secrets Manager | storage, per secret | 30 images kept, 1 secret | negligible |

Things deliberately left out because they cost more than they give at this size: a NAT per AZ, Multi-AZ Redis, a separate Dagster Postgres (RDS), ECR/STS interface endpoints, CloudTrail S3 data events.

## Security

### What is in place

- **No static credentials anywhere.** Pods use IRSA; CI has no cloud credentials at all and never plans or applies; the Redis AUTH token is generated by Terraform, stored in Secrets Manager, and reaches pods as a mounted Secret file.
- **Least privilege per workload** (`modules/iam`). Each role can `GetObject` only on its prefixes and `PutObject` only where it writes. Every role has plain `s3:ListBucket` on this single-purpose bucket: without it S3 answers a read of a missing key with 403 instead of 404, so "pointer not written yet" would look like "access denied"; listing shows key names only, never content, and object reads stay limited to the role's prefixes. Roles can also use the bucket's KMS key only via S3. No role can delete objects. A variable validation rejects any prefix that does not end in `/`, so no role can be granted the whole bucket by accident. Trust policies pin both the service account (`sub`) and the audience (`aud`).
- **Pods cannot use the node's role.** IMDSv2 required with hop limit 1, and the egress NetworkPolicy excludes the metadata address.
- **The cluster role can use the Secrets key** (Encrypt, Decrypt, ListGrants, DescribeKey on that one key) and nothing else in KMS.
- **Network.** Nodes and Redis are in private subnets; the API endpoint is private unless operator CIDRs are listed (and `0.0.0.0/0` is rejected by validation); Redis accepts only the cluster security group; the default security group has no rules; NetworkPolicies deny ingress and egress by default. Ingress: only platform pods reach the feature API, plus a labelled ingress namespace for the model API. Egress: DNS to kube-dns; HTTPS (S3, STS) for the three workloads, to any address on port 443, because AWS endpoints are not a fixed IP set; the Redis port only from the feature API and the worker, and only to the private subnets (which, with the VPC CNI, also hold pod IPs). The Terraform installs the VPC CNI as a managed add-on with `enableNetworkPolicy`, the agent that enforces them; without it they would be inert. Not tried on a live cluster.
- **Encryption.** S3 SSE-KMS with a customer key and a TLS-only bucket policy; Redis at rest and in transit; EKS Secrets envelope-encrypted with KMS; EBS root volumes encrypted; ECR with KMS; log groups with a separate KMS key.
- **Workload hardening.** Namespace enforces the `restricted` Pod Security Standard; containers run as UID 10001 with a read-only root filesystem, no privilege escalation, all capabilities dropped, seccomp `RuntimeDefault`, no service-account token mounted.
- **Supply chain.** Immutable ECR tags with scan-on-push; CI pins tool versions and verifies the kustomize and kubeconform downloads by SHA-256; provider versions are locked (`.terraform.lock.hcl`, three platforms); gitleaks scans every push.
- **Serving.** The model is JSON scored with numpy: loading a model never unpickles anything from the bucket. The job API accepts only known job kinds.

### Checkov results and the skips

CI runs checkov on the Terraform and on the rendered dev manifests and fails on any finding. Terraform skips are inline next to the resource, each with its reason; in short:

| check | why skipped in dev |
|---|---|
| CKV_AWS_111, 356, 109 on the two KMS key policies | key policies use `Resource: "*"` to mean "this key"; the account root administers it |
| CKV_AWS_338 (1-year log retention) | 30 days in dev for cost; set `log_retention_days = 365` in prod |
| CKV_AWS_394 (pin AZ identities) | subnets are created once; an AZ change is a deliberate, reviewed replan |
| CKV2_AWS_50 (Redis Multi-AZ) | dev runs one node; `redis_replicas >= 1` enables failover |
| CKV2_AWS_57 (secret auto-rotation) | ElastiCache AUTH rotation is a two-phase runbook procedure |
| CKV_AWS_18, CKV2_AWS_62, CKV_AWS_144 (bucket access logs, event notifications, cross-region replication) | dev; everything in the bucket can be rebuilt by the pipeline. Prod plan: CloudTrail data events for the bucket |

Kubernetes skips (command line in CI):

| check | why |
|---|---|
| CKV_K8S_43 (image by digest) | ECR tags are immutable, so a tag already names one image; digests make the overlay unreadable |
| CKV_K8S_15 (pull policy Always) | same reason; `IfNotPresent` avoids a registry call per pod start |
| CKV_K8S_9 (readiness probe) | flagged only for the worker, which serves no traffic; the HTTP APIs' readiness probes are enforced by `tests/test_manifests.py` |

### Known gaps

- The Redis token is in Terraform state; the state bucket must be private, encrypted and readable only by the deploy role (`backend.tf`).
- The `redis-auth` Kubernetes Secret is created by hand from Secrets Manager; an External Secrets operator would remove that step and its room for error.
- The APIs have no authentication of their own. They are ClusterIP services behind NetworkPolicies; exposing them outside the cluster needs an authenticating ingress (OIDC at the load balancer, or a gateway) first.
- No admission policy (Kyverno, Gatekeeper) enforces the manifest rules in the cluster; they are enforced in CI only.
- Nothing scans the Python dependencies for CVEs in CI; ECR scan-on-push covers the built image once it is pushed.
